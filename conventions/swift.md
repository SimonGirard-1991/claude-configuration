# Swift conventions

Swift on Apple platforms, for projects built from scratch. The bar is an app a top-tier
team would ship: free of data races, accessible, and tested where its logic lives. API and
version facts come from current Apple and swift.org documentation (Context7 first), never
from memory: Swift, Xcode and the SDKs change every year. These conventions do not
apply to the native shell of a React Native app.

## Stack

- Each project records its tool versions and OS floors: the Xcode version (which ships the
  compiler, swift-format and the SDKs) and the exact XcodeGen version in the README,
  `options.minimumXcodeGenVersion` in `project.yml` set to that version,
  `// swift-tools-version: 6.2` in each package, and the minimum OS versions in
  `options.deploymentTarget` and the package's `platforms:`. Once a project has CI or a
  second machine, its tooling pins XcodeGen to that version.
- The compiler is Xcode's Swift 6.x. The language mode is Swift 6 (`SWIFT_VERSION: "6.0"`,
  `swiftLanguageModes: [.v6]`), which makes complete concurrency checking unconditional
  and its findings errors. Warnings are errors too: `SWIFT_TREAT_WARNINGS_AS_ERRORS: YES`,
  `.treatAllWarnings(as: .error)`.
- Concurrency settings are explicit per target. App targets set
  `SWIFT_DEFAULT_ACTOR_ISOLATION: MainActor` and `SWIFT_APPROACHABLE_CONCURRENCY: YES`,
  which turns on `NonisolatedNonsendingByDefault` and `InferIsolatedConformances`. The
  core package keeps the default nonisolated isolation and enables the same two with
  `.enableUpcomingFeature("…")`. A misspelled feature name is ignored without a warning, so
  copy the names exactly.
- XcodeGen's `project.yml` is the source of every app target. The `.xcodeproj` is
  generated by `xcodegen generate`, gitignored, and never edited.
- Domain or game logic lives in an SPM core package under `Packages/`, which imports no UI
  framework. Its types are `Sendable` values, and `swift test` runs its tests with no
  simulator. The app target renders state and turns input into calls on the core.

## Concurrency

- Shared mutable state lives in an actor, and UI state in a `@MainActor` type.
- No `@unchecked Sendable` and no `nonisolated(unsafe)`: each switches the compiler's
  checking off.
- Structured concurrency first: `async let` and task groups. No `Task.detached` and no
  `DispatchQueue` in new code. A `nonisolated` async function runs on its caller's actor,
  so work that must leave the main actor goes in an actor, or in a function marked
  `@concurrent`. What that function calls lives in the core package or is declared
  `nonisolated`, since the app target's types are main-actor isolated.
- An actor's state, the main actor's included, can change at every `await`. Re-check what
  the code relied on after each suspension, and never leave an invariant broken across one.
- An async result is applied only while its request is current. After the last `await`,
  check `Task.isCancelled` or compare an id or a generation before writing it. Cancelling
  a task, as `.task(id:)` does when the id changes, only asks it to stop: a cancelled task
  that does not throw still returns, and SwiftUI does not wait for it.
- SwiftUI cancels `.task { }` and `.task(id:)` with their view, so work tied to a view runs
  there, as `.task { await model.run() }` with `run()` checking cancellation. A `Task { }`
  is unstructured wherever it is created, inside those included, and is not cancelled with
  its creator. Its owner keeps the handle (`@ObservationIgnored` in an `@Observable`
  model), and cancels it before starting a replacement, when the work should stop and in
  `deinit`.
- A stored task's capture follows the lifetime the owner needs. A long-running one must
  not keep its presentation model alive: it captures `[weak self]` and holds `self`
  strongly only inside each short step after an `await`. A weak capture alone is not
  enough: `await self?.run()` keeps the owner alive for the whole call. A finite task whose
  work must finish, such as a save, captures `self` strongly on purpose, since a weak
  capture would drop the work when the screen closes.
- Long work respects cancellation: `try Task.checkCancellation()` or `Task.isCancelled` in
  its loops.

## Types

- Value types by default. A class is `final` and has a reason: identity, or an API that
  demands one.
- No `!`, `try!` or `as!`, tests included. App code unwraps with `guard let` or `if let`
  and makes an impossible state unrepresentable rather than force it. Tests unwrap with
  `try #require(…)` (`XCTUnwrap` in XCTest) and call throwing code with `try`: a failed
  force unwrap crashes the whole test run.
- Domain models are `Sendable` values in the core. `@Observable`, never
  `ObservableObject` or `@Published`, is for the `@MainActor` presentation models views
  observe. A view that creates its model owns it in `@State`. A view handed one takes it
  as a plain property through its initializer, or as `@Bindable` when it needs bindings
  such as `$model.name`. `@Environment` carries what many views share, not every
  dependency.
- Time and randomness are injected. Sleeps and timeouts take an `any Clock<Duration>`
  (`ContinuousClock` in production), and "now" arrives as a parameter. Randomness takes a
  `RandomNumberGenerator`, seeded in tests. The standard library has no seedable one, so
  write a small generator struct (SplitMix64), `Sendable` by construction.

## Testing

- Swift Testing for every unit test: `@Test`, `#expect`, `try #require`, and
  `@Test(arguments:)` for cases that differ only in data.
- XCTest only for UI tests (`XCUIApplication`) and performance tests, which Swift Testing
  does not cover. Never mix the two frameworks' APIs in one test.
- Tests run in parallel, so each owns its resources: its own temporary directory, store
  and fakes, and no shared singleton or global state. `@Suite(.serialized)` is for a suite
  whose tests must share something that cannot be isolated, and every test that touches it
  goes in that one suite.
- Each test marks its phases as `~/.claude/CLAUDE.md` defines the markers.

## Accessibility

An inaccessible screen is broken, not unfinished.

- VoiceOver: every control has a label that names its action, icon-only buttons included.
  Decorative images are hidden with `.accessibilityHidden(true)`. State a sighted player
  reads off the screen, such as a board, a score or a timer, is exposed with
  `.accessibilityValue(_:)`. A value that changes too often to announce, such as a running
  timer, also takes `.accessibilityAddTraits(.updatesFrequently)`, so VoiceOver reads it on
  demand, and is never announced on every tick. A score that changes now and then does not
  take it. `AccessibilityNotification.Announcement` is for a change the player must hear at
  once, such as a new level or time running out.
- Dynamic Type: text uses text styles (`.font(.body)`), custom dimensions scale with
  `@ScaledMetric`, and layouts hold at the largest accessibility sizes.
- Reduce Motion: read `@Environment(\.accessibilityReduceMotion)`, and replace large or
  flashing animation with a fade or none.
- Contrast: text meets WCAG AA (4.5:1) in light, dark and Increase Contrast, and colour is
  never the only carrier of meaning, such as a piece type or a mine count.
- tvOS: every control is reachable by focus, the focused one is visibly distinct, and focus
  moves predictably (`@FocusState`, `.focusable()`, `.focusSection()`).

## Formatting

`swift format lint --strict --recursive <source roots>` passes against a committed
`.swift-format`. Name the roots (the app, `Packages`, the tests), never `.`: swift-format
ignores `.gitignore` and would reach Xcode's generated sources under `build/`.

## Verification after non-trivial changes

1. `swift test --package-path Packages/<Core>` when the core changed.
2. `xcodegen generate` before every build, so no added, removed or moved file is missed,
   then `xcodebuild test -scheme <App> -destination '<destination>'`, for example
   `platform=iOS Simulator,name=<device>`.
3. `swift format lint --strict --recursive <source roots>`.
4. `try app.performAccessibilityAudit()` checks only the screen shown when it runs. A UI
   test therefore navigates to each changed screen and state, the modal, empty and error
   states the change touches included, and audits each. The hand-back asks the user to
   walk the flow with VoiceOver and the largest text size, which no audit replaces.
5. Run the self-review loop below, telling `code-reviewer` this is a **Swift diff** so it
   applies its Swift lens. A fix made during the review reruns each step above that covers
   what it changed before it goes back to the reviewer.

### Self-review loop

Spawn `code-reviewer` with: what changed and why, the calibration tier
(throwaway / internal tool / production service / critical financial system), the scope
(paths or git range), and the line `Invocation: self-review loop, iteration N of 3`.
Address 🔴 and 🟡; judge 🔵 on merit; cap at 3 iterations, then escalate to the user with
what is outstanding. A verdict covers only the diff it saw: every edit after a review goes
back through the reviewer within the cap, a 🔴 fix without exception; past the cap, hand
the fix to the user marked unreviewed. The loop adds no quality of its own: submit correct
code first, and mid-loop fix only the accepted findings, adding nothing new.
