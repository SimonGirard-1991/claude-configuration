# ~/.claude — config layout

Personal Claude Code configuration. This directory is a git repo; `.gitignore` keeps secrets and ephemeral state out.

## What's tracked

| Path | Purpose |
|---|---|
| `agents/` | Custom subagents, both `model: inherit`: `code-reviewer` (read-only staff review of a diff) and `learning-doc-writer` (pandoc-ready learning docs). Maintainer notes and the decision log live in `AGENTS.md`. The four architect agents were retired 2026-09-09 — see that file. |
| `skills/` | User-scope skills: `hexagonal-ddd-java`, `hexagonal-module-bootstrap`, five `java-*` skills (testing-strategy, observability, reliability-messaging, performance-patterns, security-baseline), `client-comms` (client-facing register, five message structures, French business conventions), and `scoping` (`disable-model-invocation`, invoked as `/scoping <brief>` — discovery questions, out-of-scope lists, three-point estimates, calibration tier). |
| `rules/` | User-scope rules: `java.md` (stack conventions, delegated `java-*`/`hexagonal-*` skills, the post-change verification protocol), `frontend.md` (React / Next.js App Router on the repo's installed majors, TS strict, the fire-on-sight anti-pattern list, WCAG 2.2 AA checklist, money and date correctness, TanStack cache strategy) and `shell.md` (the four hard script rules, bash 3.2 portability floor, zsh dialect). `java.md` and `frontend.md` are injected at session start by `hooks/session-rules.sh` when the repo is Java or React/Next, and keep their `paths:` frontmatter only as a fallback: a path-scoped rule loads when the Read tool opens a matching file, which auto mode rarely does. `shell.md` has no `paths:` and loads in every session, because scripts turn up in any repo. `code-reviewer` carries the matching frontend lens, as it does for scripts. |
| `hooks/` | Hook scripts wired via `settings.json`. `bash-guard.py` (PreToolUse on Bash — deny credential-printing commands, environment dumps and catastrophic `rm -r`; ask on force or deleting pushes, `reset --hard`, `git clean`, `rm -r` of the working directory or a `.git`, and shell access to secret files. Judged per command segment, deny beats ask, and it runs on `/usr/bin/python3` so a repo's pyenv pin cannot switch it off). `reviewer-guard.py` (PreToolUse, wired from `code-reviewer`'s own frontmatter rather than `settings.json`, so it runs only while the reviewer does — Edit/Write land only in its memory directory or scratch, and Bash gets a read-only allowlist for `git` plus denials for in-place edits, editors, `eval`, `sh -c`, write-capable `gh`, and redirects or `tee` into the repo; fails closed). `session-rules.sh` (SessionStart, one entry per rule — injects `rules/java.md` or `rules/frontend.md` when the session's repo is Java or React/Next, since a path-scoped rule loads only on a Read-tool read; one rule per invocation keeps each under the 10,000-character hook output cap; each injection is logged to `logs/rules.jsonl`, and anything that goes wrong surfaces as a `systemMessage`). `log-instructions.sh` (InstructionsLoaded, no matcher — appends every CLAUDE.md, rules-file and imported-file load to the same log; AGENTS.md, read directly as project instructions here, fires no event and leaves no line; its one CLAUDE.md line per session is what proves it alive). **The rest run on `Stop`, not `PostToolUse`**: an `Edit|Write` matcher cannot see file changes made through Bash, and under `defaultMode: auto` the harness steers most edits there — 387 Bash-shaped writes against 263 Edit+Write calls over the fortnight before the switch. A Stop hook reads `git status --porcelain -z -uall`, so it sees the turn's result whatever tool produced it, untracked files included. `on-stop-validate.sh` (Stop, plus SubagentStop for the listed editing agents — scoped to this repo; drives `validate-skill-tree.sh`, `validate-readme.sh` and `validate-rules.sh` over the changed set, exit 2 feeds findings back). `validate-skill-tree.sh` (runs `scripts/lint_skills.py` scoped to each changed skill, blocking on its ERROR tier only). `validate-readme.sh` (checks this file against the repo: every tracked top-level entry and every hook is named here, and nothing this table claims is gitignored). Both take paths as arguments for that, and still read a PostToolUse payload on stdin when called with none. `validate-readme.sh` resolves a relative path against the working directory, and when every path it is given falls outside the repo it says "nothing checked" rather than exit 0 in silence. `validate-rules.sh` (blocks a turn that leaves `rules/java.md` or `rules/frontend.md` too big for `session-rules.sh` to inline. It runs that hook itself against a throwaway repo, and a change to the hook re-checks both rules, so the cap and header cannot drift from the check. It takes paths only, with no stdin form). `format-on-stop.sh` (Stop — repo-local prettier over the changed set in one invocation, only when the repo has a prettier config; Java/spotless deliberately not hooked, too slow to sit in a turn; never blocks. The changed set is everything `git status` lists, so your own uncommitted edits in that repo get formatted too, not only the turn's; a per-turn snapshot was considered on 2026-09-27 and not built). `sonar-gate-on-stop.sh` (Stop — runs `scripts/sonar-gate.sh` so a turn cannot end with new Sonar findings; inert unless the repo has a `.sonar-gate` file. Trigger, suppression scan and findings filter all read one file set — `git diff` against the fork point plus `ls-files --others` — so it never blocks on a file it did not read, nor on pre-existing findings in files the turn never touched. The fork point comes from `origin/HEAD`, else `main`, else `master`. A green run leaves a fingerprint in `$TMPDIR` — base commit, changes to java sources, poms and contract schemas, `.sonar-gate`, the gate and the hook — so a Stop that changed none of those skips the scan; anything else the build reads is outside it. Blocks on unjustified `NOSONAR`/`@SuppressWarnings`; a reason on the same line passes and is echoed for the hand-back. Never boots the container: a stopped SonarQube reports "checks are OFF" rather than passing silently). Tune patterns in the scripts, not in `settings.json`. |
| `scripts/` | Repo tooling: `lint_skills.py` (the skill-tree linter behind `validate-skill-tree.sh`), `test_lint_skills.py` (its fixture suite — add the fixture before the check, or a check can silently match nothing while reporting success), `test_hooks.py` (black-box fixture tables for the hooks, pinning what each must catch and what it must let through; `CLAUDE_BASH_GUARD`-style overrides test a candidate before it replaces a live guard), and `sonar-gate.sh` (runs the real Sonar analyzers over a Maven project against a local SonarQube container; the oracle behind `sonar-gate-on-stop.sh`, also usable by hand — `--facets` prints the rule distribution, which is how the authoring rules in `java-testing-strategy` get refreshed from evidence, and `--files` restricts the findings, the count and the exit status to a list of repo-relative paths. When it cannot wait for its own analysis it exits 1, rather than answer from the previous one; with `--files` it reads every page of issues, and past the 10000 the API serves it exits 1 too). |
| `settings.json` | User-scope settings: permission allow/ask/deny lists (deny covers `.env*`/`.envrc`/`.credentials.json` reads+edits; ask covers `.pem`/ssh-key reads), hook wiring, model/effort defaults, plugin enablement, and `syncClaudeAiPlugins: false` (plugins enabled on the claude.ai account stay there and in Cowork; in Claude Code their ~90 skills and ~80 MCP servers overflowed the skill listing, so descriptions of skills actually in use were being cut). Contains no secrets — safe to track. Note: pre-approved session dirs (e.g. the scratchpad) can bypass deny rules — they protect real project/workspace paths. |
| `CLAUDE.md` | Cross-project notes loaded into **every** session — kept deliberately short, because every line costs tokens in every session on this machine. Anything project-specific still belongs in that project's own `CLAUDE.md`. |
| `AGENTS.md` | Maintainer notes: the two agents, the reviewer memory protocol, and the dated decision log. Loads as project instructions only in sessions started in `~/.claude` (~4.7k tokens), which is intended. |
| `.gitignore` | An allowlist: `/*` ignores every top-level entry and `!/` lines re-admit the tracked ones, so state Claude Code adds beside the config stays out by default. Secret-file patterns (`.env*`, `*.token`, `.credentials.json`) still apply inside tracked directories. Add a tracked top-level entry and it needs both a `!/` line and a row in this table — `validate-readme.sh` enforces the row. |
| `README.md` | This file. |

## What's NOT tracked (gitignored)

Everything the table above does not name. The ones worth knowing: `agent-memory/` (persistent per-agent memory — `MEMORY.md` index + entries; personal calibration data, stays local), `plans/` (saved implementation plans — local working state; delete them when done, old plans rot), `settings.local.json`, `projects/` (transcripts and per-project auto-memory), `plugins/` (all of it — `installed_plugins.json` is derived state whose recorded SHAs churn on every commit; plugin *enablement* is tracked via `settings.json`), `skills/synced/` (skills synced from claude.ai — Anthropic-licensed, never republish), `uploads/` (images pasted into sessions), `logs/`, credentials, `.env*`. The remote is public: treat anything that is not in the table as private.

## MCP servers — where they actually live

All four servers are user scope, in `~/.claude.json` (outside this repo), added with `claude mcp add -s user`. There is no project scope: the old `.mcp.json` held only a second playwright and was removed on 2026-09-24. There is no local scope either. A local entry outranks the user entry of the same name and replaces it whole, launch line included, so an unpinned local copy undoes the pin in that project. The last two, an `@latest` playwright and a duplicate fal-ai, were removed on 2026-09-26.

| Server | Launch | Notes |
|---|---|---|
| `context7` | `npx --prefix / -y @upstash/context7-mcp@4.1.1` | Library docs lookup. Allowed to both agents. |
| `brave-search` | Wrapper brave-mcp.sh in `~/bin`, which runs a local install of `@brave/brave-search-mcp-server@2.1.4` in `~/tools/brave-mcp` | Web search. Allowed to `learning-doc-writer`. Kept over the built-in `WebSearch` by decision 2026-09-09, though the agents that leaned on it hardest are retired — revisit if `/usage` shows no attribution. |
| `playwright` | `npx --prefix / -y @playwright/mcp@0.0.82` | Browser automation. Plain `npx` rather than an absolute nvm path, so a Node upgrade cannot break it. |
| `fal-ai` | Wrapper fal-mcp.sh in `~/bin`, which runs a local `fal-ai-mcp` install in `~/tools/fal-mcp` | Image, video and audio generation. |

brave-search and fal-ai, the two servers that hold keys, run from local installs with a `package-lock.json`, so their whole dependency tree moves only when the install is updated. Those lockfiles exist only on this machine: on a new one, the installs resolve afresh. context7 and playwright are pinned to an exact version, so a new release cannot land unannounced, but their dependencies are not: npx resolves them afresh whenever it creates a new install directory — a pin bump, a new machine, a cleared `~/.npm/_npx` — so a bump installs whatever the dependency ranges allow that day. `--prefix /` keeps a project's `.npmrc` out of those two launches: npx fetches package metadata at every start, from the registry the launch directory's config names, so a project pointing at an unreachable registry would stop both servers starting there. The flag also points npm's global config at `/etc/npmrc`, so a registry or token set with `npm config set -g` would not reach them; `~/.npmrc` still does. The servers themselves still start in the project directory, and playwright's workspace and `.playwright-mcp/` output follow the first MCP root Claude Code offers, the directory the session started in.

Bump the pins about every six months; nothing schedules this. For context7 and playwright, `claude mcp remove <name> -s user`, then `claude mcp add -s user <name> -- npx --prefix / -y <package>@<version>`. For brave-search and fal-ai, run `npm install --save-exact --ignore-scripts <package>@<version>` in their `~/tools` directory, which rewrites the lockfile; the wrappers run the package's bin entry, so they need no change. Never re-add either of those two without its wrapper: the key reaches each server only through it (brave-search exits at startup without one), and the tempting fix, `-e`, would write the key into `~/.claude.json`. Then update the versions in the table above, and check that `claude mcp list` shows each server connected. Last, list the projects that carry local-scope servers, which should print nothing, or only deliberate pinned overrides: `jq -r '.projects | to_entries[] | select((.value.mcpServers // {}) | length > 0) | .key' ~/.claude.json`.

Agents reference these via `mcp__context7__*` / `mcp__brave-search__*` in their `tools:` frontmatter — the allowlists are not uniform, so check the specific agent when a tool appears missing. If a pattern stops matching anything at all, the server itself may have been removed or renamed in `~/.claude.json`.

### claude.ai connectors
Connector policy (ask rules on outbound, hard-to-undo connector tools, and denied connectors) lives in machine-level managed settings, `/Library/Application Support/ClaudeCode/managed-settings.json` — outside this repo on purpose, because the repo is public and the rules would name personal accounts. Ask rules are evaluated before the auto-mode classifier, so those calls always reach a human.

## Secrets

- MCP keys live in the **macOS Keychain**, and no Claude session inherits them: a wrapper in `~/bin` reads the item and `exec`s the server, so only that server's process tree has the key in its environment. brave-mcp.sh reads `brave-api-token` and starts its server from `/`, out of reach of a project's `.env`; fal-mcp.sh reads `fal-api-key`, and its server loads no `.env`. No shell rc or launcher exports either key. The chain is Keychain → wrapper → MCP server.
- The Keychain is not a boundary against this user. An item created with `security add-generic-password` trusts `/usr/bin/security` by default, so any process running as this user can read it without a prompt while the keychain is unlocked, a session's Bash included. What stands in the way is `permissions.deny` in `settings.json` and `bash-guard.py`, and both match the command's text.
- Never put a key value in `settings.json`, `~/.claude.json` or any other file on disk, and never in argv, which `ps` shows.
- To rotate, issue a new key with the provider first, then replace the item: `security delete-generic-password -s brave-api-token`, then `security add-generic-password -a "$USER" -s brave-api-token -w`. With `-w` last, `security` prompts for the value, so it reaches neither shell history nor argv. A running server keeps the old key until its session restarts, so revoke the old key only after restarting. fal-ai works the same way with `-s fal-api-key`.

## Agent memory policy

Both agents set `memory: user`, so Claude Code injects the generic memory instructions and the `MEMORY.md` index itself — the agent files carry only what is specific to this setup. The standing policy is "default is not save": memory is for things that would change behavior in a *future, different* conversation. Project-specific facts belong in the project's `CLAUDE.md`, not in user-scope memory. Reviewer writes are gated by invocation context — invoked directly by the user it saves its own memories; inside a self-review loop it ends with a **Proposed memory** note that the invoking session records only on user approval (see `AGENTS.md` § Reviewer memory protocol).

## Top-level `CLAUDE.md`

This file was deliberately absent until 2026-07 (per-project `CLAUDE.md` keeps conventions scoped; the old rule was "revisit if genuinely cross-project preferences emerge"). What earns its place today: the comment doctrine and its one exception, test phase markers (decided 2026-08-11, amended 2026-09-24 — see the `AGENTS.md` decision log). It is language-agnostic, it applies to every session on this machine, and removing it measurably brings the over-commenting back. Beside it goes only what passes the admission test: a preference that applies in every session whatever the repo, or a fact about this machine that no repo can carry. Keep the file minimal — every line costs tokens in every session, and anything derivable from the code does not belong here.
